# 高端硬件设备线上交易平台 PRD

**英文暂定名称：** Enterprise High-Value Trading Platform  
**系统简称：** EHTP  
**文档版本：** V1.0（需求设计稿）  
**项目阶段：** MVP  
**业务对象：** GPU H200 等稀缺高端硬件设备，后续可扩展其他高价值商品  
**终端范围：** 大 B 内部管理后台 + 小 b 企业客户门户  
**文档状态：** 待业务、财务、法务联合评审

---

# 1. 项目概述

## 1.1 项目背景

公司拥有 GPU H200 等高端硬件设备，但由于供货数量有限、客户需求较多，需要建立规范、透明、可追溯的线上交易平台。

平台用于发布商品信息、收集企业客户采购需求、组织竞争性报价、审核客户资格、分配有限库存，并完成合同、资金、订单、发货及售后管理。

平台不仅解决当前稀缺硬件的销售问题，还要积累大客户资源、维护客户关系、沉淀交易数据，为后续扩展其他高端商品销售业务提供统一系统基础。

## 1.2 项目目标

1. 提高真实采购需求的识别能力，降低无效申报、中选后取消及恶意占位。
2. 建立可配置、可审计的商品竞争性分配机制。
3. 规范运营、销售、财务、法务、仓储及售后岗位的协作流程。
4. 实现竞价结果、合同、资金、订单、库存和发货之间的完整关联。
5. 明确每项关键操作的责任人、审批人和操作依据。
6. 形成统一的大客户档案、商品资料库和客户跟进记录。
7. 为后续新增商品品类、移动端通知及外部业务系统集成预留扩展能力。

## 1.3 项目范围

### MVP 包含

- 员工账号、角色、权限及审批配置。
- 企业客户注册、资料审核及客户负责人分配。
- 高端商品、产品资料及库存管理。
- 竞价活动创建、发布、报名、申报及审核。
- 竞价规则配置、结果评审、中选及候补管理。
- 保证金登记、财务核验及退还流程。
- 合同审批、正式订单及付款计划管理。
- 库存锁定、发货审批、出库、物流及签收。
- 售后工单、业务操作日志和审计报表。
- 企业门户中的产品浏览、申报、结果和订单查询。
- 业务通知、超时提醒和异常处理。

### MVP 暂不包含

- 移动端小程序的完整开发。
- 自动接入银行并实时识别到账。
- 自动电子签约，除非后续明确接入服务商。
- 完整 ERP、WMS 或财务系统替代。
- 面向所有商品的开放式实时升价拍卖。
- 无人工复核的自动化资金放行。
- 未经确认的复杂信用评分、机器学习风险评分或自动定价。

上述能力可以预留接口，但不得成为 MVP 正常交易流程的前置依赖。

# 2. 业务原则与待确认事项

## 2.1 核心业务原则

1. 注册客户可以浏览公开信息和提交注册资料，但不能因此自动获得竞价资格。
2. 竞价前应公布适用规则、商品数量、报价要求、保证金条件、评审方式及重要时间节点。
3. 竞价结果必须依据事先确定的规则生成，不允许在结果产生后临时改变排序标准。
4. 中选结果不等于合同生效，也不等于允许发货。
5. 保证金、预付款、货款和退款必须分别记录，不得混为一个金额字段。
6. 实际收款应以财务认可的到账依据为准，不能仅凭客户付款截图认定。
7. 订单数量、商品批次、付款条件及发货数量必须可核对。
8. 关键业务操作必须记录执行人、时间、操作内容、变更前后值及相关审批。
9. 高风险操作应执行职责分离和必要的双人复核。
10. 已发布或已生效的关键业务记录不得被普通用户直接覆盖或删除。

## 2.2 待确认决策清单

| 编号 | 决策事项 | 责任方 | 对开发的影响 |
|---|---|---|---|
| D-01 | 竞价采用综合评分还是分层排序 | 业务 | 决定结果计算引擎 |
| D-02 | 报价是否设置最低成交价及有效区间 | 业务、财务 | 决定报价校验规则 |
| D-03 | 采购能力如何认定，是否需要证明文件 | 业务、财务 | 决定客户审核字段 |
| D-04 | 保证金金额、比例、缴纳时间和退还期限 | 业务、财务、法务 | 决定资金流程 |
| D-05 | 未中选、中选后取消及违约时保证金如何处理 | 财务、法务 | 决定退款与争议流程 |
| D-06 | 保证金能否抵扣货款 | 财务、法务 | 决定应收及收款核销模型 |
| D-07 | 是否允许分批付款、分批发货 | 业务、财务 | 决定订单与出库模型 |
| D-08 | 中选后签约及付款的时间限制 | 业务、法务 | 决定超时及候补机制 |
| D-09 | 候补客户递补的具体条件与顺序 | 业务、法务 | 决定库存释放规则 |
| D-10 | 合同与线上申报不一致时的优先依据 | 法务 | 决定争议处理制度 |
| D-11 | 商品库存以本系统还是外部 ERP 为准 | 业务、技术 | 决定数据权威来源 |
| D-12 | 员工兼岗时的审批和复核要求 | 管理层、内控 | 决定权限矩阵 |
| D-13 | 客户、合同及审计数据的保存期限 | 法务、信息安全 | 决定数据保留和归档 |
| D-14 | 高端 GPU 的客户及最终用途合规审核规则 | 法务、合规 | 决定交易拦截条件 |

在上述决策未完成前，系统应支持配置或保留待配置状态，不得自行推定为已获批准的正式规则。

# 3. 用户角色与使用端

## 3.1 大 B：公司内部管理后台

供公司内部人员管理客户、商品、竞价、审核、订单、资金、库存、发货及售后。

## 3.2 小 b：企业客户 PC 门户

供企业客户注册、维护公司资料、浏览商品、参加竞价、提交申报、查看中选结果、补充资料和查询订单。

同一企业可以拥有多个用户账号，由企业管理员维护授权关系。企业用户只能访问本企业有权查看的数据。

## 3.3 内部角色

- 平台管理员
- 运营人员
- 销售人员
- 财务人员
- 法务人员
- 仓储／发货人员
- 售后人员
- 业务审批负责人
- 审计人员（可选只读角色）

角色与具体员工之间应通过授权关系管理，不将角色直接写死在业务代码中。

# 4. 核心业务流程

## 4.1 企业注册与准入

1. 企业用户注册账号。
2. 填写企业名称、统一识别信息、企业地址、联系人及授权信息。
3. 上传必要的资质文件。
4. 系统生成企业档案和审核任务。
5. 运营人员检查资料完整性，必要时要求补充资料。
6. 授权审核人确认企业身份及准入条件。
7. 审核通过后，企业获得相应的客户状态和业务权限。
8. 系统分配内部销售负责人、运营负责人及售后负责人。
9. 企业信息变化时，按规则重新审核。

**业务要求：** 允许所有客户发起注册，不等于所有客户都可参与所有竞价。具体活动可以要求更高等级的资格、指定邀请或额外合规审核。

## 4.2 商品维护与发布

1. 运营人员创建商品档案。
2. 录入品牌、型号、规格、产品说明及适用的合规信息。
3. 上传产品图片、性能资料、视频、安装说明及售后政策。
4. 维护商品批次、可用数量、库存状态和序列号管理要求。
5. 指定适用的交易方式及商品交付条件。
6. 提交商品发布审批。
7. 审核通过后对客户门户展示。

商品库存必须区分：

- 实际在库数量
- 已锁定数量
- 已分配未交付数量
- 已出库数量
- 可分配数量

可分配数量的计算方式应与实际库存模型保持一致，不得仅根据商品页面上的手工填写数量决定能否成交。

## 4.3 竞价活动创建

运营人员创建竞价活动，至少设置：

- 活动编号及名称。
- 对应商品及批次。
- 本次计划分配数量。
- 客户报名及申报起止时间。
- 报价方式、报价单位及报价精度。
- 价格下限或有效报价范围（如适用）。
- 客户资格要求。
- 保证金要求及缴纳时间。
- 采购需求及履约能力审核要求。
- 评审和分配规则版本。
- 评审时间及结果通知时间。
- 中选后签约、付款及确认期限。
- 候补规则及超时处理方式。
- 取消活动和异常处理规则。
- 相关合同条款、申报模板及附件。

活动规则须经过授权审批。活动发布后，关键规则原则上不得直接修改。

如确需调整，应按照经批准的变更制度处理，保留原版本、变更理由、审批记录及客户通知；涉及公平性或交易条件的重大变更，应由业务和法务确认是否需要取消并重新发布活动。

## 4.4 客户申报

企业客户：

1. 阅读商品信息和活动规则。
2. 确认企业身份、授权联系人及采购承诺。
3. 填写采购用途、需求数量、报价及交付要求。
4. 按要求上传申报文件。
5. 阅读并确认适用的保证金和交易条款。
6. 提交申报。
7. 获取申报编号及回执。

系统应在服务端检查申报截止时间、客户资格、字段完整性、报价格式、数量限制和重复提交。

提交成功后生成不可重复的申报记录。允许补充资料时，应保留原始提交内容及后续修改版本。

## 4.5 真实需求审核

运营和销售根据授权分工审核：

- 企业资料是否真实、完整。
- 联系人是否具有适当授权。
- 申报数量与采购用途是否合理。
- 客户是否具备相应的采购和履约能力。
- 是否存在重复申报、关联主体占位或异常行为。
- 必要的最终用户、最终用途和交易合规条件是否满足。
- 需要补充的合同、证明文件或付款承诺是否已提交。

审核结果包括通过、补充资料、不通过或待专项审核。

不通过时必须填写原因和处理依据。涉及客户信用、违规或资格限制的结论，应由授权人员复核，不得仅依赖自动规则。

## 4.6 评审与库存分配

1. 到达截止时间后，系统冻结本轮有效申报。
2. 系统检查报价及申报完整性。
3. 根据已批准的评审规则计算候选结果。
4. 生成评审明细、拟中选名单及候补名单。
5. 授权评审人员核验计算结果及异常情况。
6. 由审批负责人确认结果。
7. 系统锁定对应数量的库存，并记录锁定期限。
8. 通知客户结果和下一步要求。

评审规则可以采用“资格门槛 + 价格优先 + 履约能力审核”的方式，也可以采用经批准的综合评分。

**不得在规则未确定前，直接将报价、采购数量和采购能力随意加权。** 各项指标、权重、评分方法、并列处理及人工复核范围必须在活动发布前明确。

系统需要记录：

- 规则版本。
- 输入数据快照。
- 计算结果及排序依据。
- 人工调整及理由。
- 评审人和批准人。
- 结果发布时间。

如涉及人工调整，必须保留原始系统结果与最终批准结果，避免无法解释中选差异。

## 4.7 保证金、合同及付款

1. 客户按活动规则缴纳保证金。
2. 客户提交付款凭证或相关信息。
3. 财务核验实际到账金额、付款主体、到账时间及资金用途。
4. 中选后进入商务和合同确认流程。
5. 合同完成所需审批及签署后生效。
6. 系统根据合同生成应收计划。
7. 客户按约定付款。
8. 财务核验实际收款，并关联相应应收项目。
9. 满足约定的发货条件后，订单进入待发货审批。

保证金必须与货款分开记录。保证金抵扣货款、退还、没收或争议处理均须有明确依据及审批记录。

如客户中选后未签约、未付款或提出取消，系统不得直接删除交易记录。应根据合同及活动规则进入逾期、取消、退款或争议处理流程。

## 4.8 发货及售后

1. 销售人员提交发货申请。
2. 系统核验订单、合同、付款、库存及审批状态。
3. 财务确认付款条件满足，或确认合同允许的其他交付条件。
4. 仓储人员复核商品型号、数量、批次及序列号。
5. 授权人员批准出库。
6. 生成出库单及物流记录。
7. 客户签收，记录实际交付数量和签收凭证。
8. 完成订单或登记部分交付。
9. 如有问题，创建售后工单并关联原订单和商品。
10. 记录售后处理、维修、退换货或争议结果。

如果合同允许分批付款、分批发货，应以对应的合同条款和已批准规则控制每一批交付，不能把部分到账直接等同于允许全部发货。

# 5. 状态机设计

状态机应由后端统一管理。前端按钮是否显示不能代替后端的状态校验。

## 5.1 企业客户状态机

| 当前状态 | 允许操作／事件 | 下一状态 | 操作要求 |
|---|---|---|---|
| 待提交 | 提交注册资料 | 待审核 | 检查必填资料 |
| 待审核 | 审核通过 | 已认证 | 记录审核人及依据 |
| 待审核 | 要求补充 | 待补充资料 | 记录补充原因 |
| 待补充资料 | 重新提交 | 待审核 | 保留版本 |
| 待审核 | 审核不通过 | 未通过 | 必须填写原因 |
| 已认证 | 触发风险审核 | 受限 | 记录限制范围 |
| 受限 | 复核通过 | 已认证 | 授权审批 |
| 已认证／受限 | 依法或依规停用 | 已停用 | 记录原因及时间 |

已认证客户的活动资格还应独立判断，避免用单一客户状态替代所有活动的准入条件。

## 5.2 竞价活动状态机

| 当前状态 | 事件 | 下一状态 |
|---|---|---|
| 草稿 | 提交审批 | 待审批 |
| 待审批 | 审批通过 | 待发布 |
| 待审批 | 审批驳回 | 草稿或待修改 |
| 待发布 | 到达发布条件 | 报名／申报中 |
| 报名／申报中 | 到达截止时间 | 已截止 |
| 报名／申报中 | 经授权取消 | 已取消 |
| 已截止 | 完成数据冻结 | 评审中 |
| 评审中 | 结果确认 | 结果已确认 |
| 结果已确认 | 进入合同履约 | 履约中 |
| 履约中 | 满足结束条件 | 已结束 |

活动可以因异常进入“异常处理中”状态，但必须记录异常类型、责任人、处理期限和恢复条件。

不允许将已经产生中选结果的活动直接删除或恢复为草稿。需要重新评审或取消时，必须通过专门的授权操作，并保留历史版本。

## 5.3 客户申报状态机

| 当前状态 | 事件 | 下一状态 |
|---|---|---|
| 草稿 | 客户提交 | 已提交 |
| 已提交 | 进入审核 | 审核中 |
| 审核中 | 资料不完整 | 待补充 |
| 待补充 | 客户重新提交 | 审核中 |
| 审核中 | 资格审核不通过 | 资格不通过 |
| 审核中 | 资格审核通过 | 资格通过 |
| 资格通过 | 活动截止并参与评审 | 评审中 |
| 评审中 | 结果确认并中选 | 已中选 |
| 评审中 | 进入候补 | 候补中 |
| 评审中 | 未中选 | 未中选 |
| 已中选 | 完成合同及交易确认 | 待履约 |
| 已中选／待履约 | 超时或取消事件 | 逾期／取消处理中 |
| 候补中 | 满足递补条件并获批准 | 已中选 |

资格审核和竞价评审是不同阶段。资格不通过的申报不得进入正常评审；已经中选的申报也不能仅因修改某个字段而被重新排序。

## 5.4 保证金状态机

建议状态：

- 待缴纳
- 待财务核验
- 已确认到账
- 部分到账（仅在业务规则允许时）
- 退款待审核
- 退款处理中
- 已退款
- 已抵扣货款
- 争议处理中
- 其他经批准的特殊状态

每笔保证金应记录应缴金额、实际到账金额、币种、付款主体、关联活动、关联客户、财务核验结果及退款或抵扣依据。

退款和抵扣均应通过独立业务记录实现，不得直接把原收款金额改为零。

## 5.5 订单状态机

| 当前状态 | 条件／事件 | 下一状态 |
|---|---|---|
| 待生成 | 中选及商务确认完成 | 待合同确认 |
| 待合同确认 | 合同达到要求 | 待付款 |
| 待付款 | 客户提交付款信息 | 待财务核验 |
| 待财务核验 | 财务确认符合合同条件 | 待发货审核 |
| 待发货审核 | 所有发货条件满足并批准 | 待出库 |
| 待出库 | 仓储完成复核并出库 | 已发货 |
| 已发货 | 客户完成签收 | 已签收 |
| 已签收 | 交易交付及必要对账完成 | 已完成 |
| 任意允许取消的状态 | 取消申请获批 | 取消处理中 |
| 取消处理中 | 资金、库存及合同事项处理完成 | 已取消 |

如允许部分付款和部分交付，应另行定义分批履约明细，不能简单复用单一的“已付款”“已发货”状态。

## 5.6 状态机通用规则

1. 所有状态转换必须通过后端业务服务完成。
2. 不允许用户通过修改请求参数绕过前置条件。
3. 每次状态转换都记录操作人、时间、原状态、目标状态和理由。
4. 失败的转换必须返回明确原因，不得静默修改数据。
5. 超时任务必须支持幂等处理，重复执行不能造成重复订单或重复退款。
6. 对于已经进入合同、付款或发货环节的交易，取消操作必须触发对应的清算和库存处理。
7. 状态定义及其可转换关系应集中管理，并通过自动化测试验证。

# 7. 数据库设计

## 7.1 设计原则

1. 使用关系型数据库管理核心交易数据。
2. 每个核心实体使用稳定的唯一 ID。
3. 金额使用精确数值类型，不使用浮点数存储货币。
4. 数量、报价单位、币种和计量单位必须明确。
5. 核心交易记录采用软删除限制或不可变记录策略，不能随意物理删除。
6. 重要字段保留创建人、创建时间、更新时间及版本信息。
7. 关键业务表通过外键或等效的完整性校验保证关联有效。
8. 文件存储与业务元数据分离，数据库保存文件 ID、版本、摘要和访问权限等信息。
9. 收款、退款、库存变更及审批记录使用独立明细表。
10. 数据库中的客户和交易隔离必须由服务端执行。

## 7.3 数据完整性约束

至少应落实以下约束：

- `event_no`、`application_no`、`order_no`、`contract_no` 等业务编号唯一。
- 同一活动、同一企业的有效申报不得重复创建，除非规则明确允许多次申报。
- 订单数量、出库数量和库存数量必须可核对。
- 收款金额和退款金额必须使用精确数值类型，并明确币种。
- 同一笔收款不能被重复核销超过其可用金额。
- 同一批库存不能被重复锁定超过可分配数量。
- 已确认的竞价规则、评审结果、合同版本和付款记录应保留历史。
- 每个审批任务应能追溯到具体业务对象和审批人。
- 企业用户访问数据时，必须验证其所属企业与业务对象之间的授权关系。
- 关键操作应支持请求幂等，避免重复提交产生重复业务记录。

# 9. 业务通知与超时管理

系统至少应支持以下通知事件：

- 企业注册审核结果。
- 竞价活动发布及报名截止提醒。
- 申报提交回执。
- 资料补充及审核结果。
- 保证金缴纳要求及核验结果。
- 竞价中选、候补或未中选通知。
- 合同签署和付款截止提醒。
- 付款核验结果。
- 发货、物流及签收状态。
- 退款进度。
- 售后受理及处理结果。
- 内部审批待办和超时升级。

每类通知应有模板、触发条件、接收对象和发送记录。

通知发送失败不得直接导致业务状态错误。系统应支持重试和失败记录，但重试不能重复生成订单、退款或库存操作。

具体通知渠道、提醒提前量和超时升级规则属于待业务确认事项。

# 10. MVP 验收标准

验收必须同时覆盖正常流程、权限控制、数据一致性和异常处理，不能只验收页面是否可操作。

## 10.1 客户管理验收

- [ ] 未登录用户不能访问受保护的企业资料。
- [ ] 企业可以提交注册资料并获得唯一企业档案。
- [ ] 资料不完整时可以退回补充，并保留审核记录。
- [ ] 审核通过后，客户才能参与符合其资格条件的活动。
- [ ] 企业 A 不能通过修改请求参数查看企业 B 的申报、合同或订单。
- [ ] 客户负责人变更后，历史负责人及生效时间仍可查询。
- [ ] 被限制或停用的客户不能继续执行受限业务操作。

## 10.2 商品及库存验收

- [ ] 商品支持规格、图片、视频及相关文件管理。
- [ ] 商品下架后，不能新建不符合规则的有效申报。
- [ ] 库存批次和序列号（如适用）可追溯。
- [ ] 锁定库存后，可分配数量按规则减少。
- [ ] 锁定超时、活动取消或交易取消时，库存按批准规则释放。
- [ ] 并发分配最后一台设备时，不会产生超卖。
- [ ] 每次库存变化都能追溯到操作人和来源业务。

## 10.3 竞价验收

- [ ] 未审批的活动不能正式发布。
- [ ] 活动规则、截止时间、商品数量及保证金要求可以查询。
- [ ] 客户不能在截止后提交新的有效申报。
- [ ] 重复提交不会产生重复的有效申报。
- [ ] 不符合报价、数量或资格要求的申报会被拒绝或进入明确的异常处理状态。
- [ ] 截止后有效申报可以被冻结并进入评审。
- [ ] 评审结果能够根据规则版本和原始数据复核。
- [ ] 人工调整必须填写理由并保留审批记录。
- [ ] 未经授权不能修改已确认的评审结果。
- [ ] 候补递补只能按照已批准的规则执行。
- [ ] 客户只能查看有权访问的活动及结果。

## 10.4 保证金及资金验收

- [ ] 保证金与货款使用不同的业务记录。
- [ ] 客户提交付款凭证后，不会自动变成财务已确认到账。
- [ ] 财务核验后能够记录金额、时间、付款依据和核验人员。
- [ ] 保证金退款必须经过适用的审核流程。
- [ ] 保证金抵扣货款时，能够追溯原收款、抵扣金额和目标应收项目。
- [ ] 同一笔收款不能被重复核销。
- [ ] 收款不足、付款逾期或付款主体异常时，系统能够拦截或进入异常处理。
- [ ] 财务人员能够查询订单的应收、实收、已核销及待处理差额。

## 10.5 合同及订单验收

- [ ] 中选结果可以生成关联的交易确认单。
- [ ] 正式订单与客户、竞价活动、申报、评审结果及合同保持关联。
- [ ] 合同变更保留版本及审批历史。
- [ ] 合同尚未达到规定条件时，不能进入不符合规则的发货状态。
- [ ] 订单数量、单价和总额计算正确。
- [ ] 未经授权不能直接修改已确认订单的关键金额或数量。
- [ ] 取消订单时，必须处理相关合同、资金及库存事项。
- [ ] 重复请求不会重复生成有效订单。

## 10.6 发货及售后验收

- [ ] 未满足发货条件的订单不能被批准出库。
- [ ] 发货申请可以关联到正式订单及审批记录。
- [ ] 实际出库数量不能超过可出库数量。
- [ ] 设备序列号（如适用）与实际发货明细一致。
- [ ] 发货后能够记录物流信息及签收凭证。
- [ ] 支持部分发货时，已发货和未发货数量能够分别查询。
- [ ] 售后工单能够关联原订单及商品。
- [ ] 退换货、退款或维修处理完成后，相关状态及库存记录保持一致。

## 10.7 权限及审计验收

- [ ] 普通员工不能自行提升角色或绕过审批。
- [ ] 销售人员不能单独完成收款核验及最终发货放行。
- [ ] 不同角色的操作范围与权限矩阵一致。
- [ ] 关键业务状态变化都有日志。
- [ ] 日志能记录操作人、时间、对象、前后值和原因。
- [ ] 普通业务用户不能随意删除关键审计记录。
- [ ] 审批记录可以追溯到具体业务对象。
- [ ] 被撤销权限的用户不能继续通过旧会话或接口执行受限操作。

## 10.8 非功能验收

以下指标应在技术评审后冻结，避免未测试就承诺性能：

- [ ] 完成身份认证、权限隔离和接口安全测试。
- [ ] 完成竞价截止时并发提交和库存竞争测试。
- [ ] 完成订单、收款、库存等关键数据的一致性测试。
- [ ] 完成重复请求、任务重试及异常恢复测试。
- [ ] 完成数据库备份及恢复演练。
- [ ] 完成关键文件的访问权限和下载控制测试。
- [ ] 明确响应时间、并发用户数、可用性及恢复时间目标。
- [ ] 明确审计日志、合同和交易文件的保留及归档策略。

## 10.9 MVP 端到端验收用例

至少使用一场测试竞价完成以下全流程：

1. 创建 GPU H200 测试商品和有限库存。
2. 创建并审批竞价活动。
3. 使用多家测试企业注册和提交申报。
4. 测试资格通过、补充资料和资格不通过。
5. 运行报价与分配规则，生成中选及候补名单。
6. 复核并批准评审结果。
7. 登记保证金，测试未到账和到账确认两种情况。
8. 生成交易确认单、合同和销售订单。
9. 测试合同未完成、付款不足时的发货拦截。
10. 财务确认符合合同要求的付款后，执行库存锁定和发货审批。
11. 完成出库、物流及客户签收。
12. 检查整个交易的客户、报价、合同、资金、库存、发货和责任记录。
13. 额外测试中选后逾期、订单取消、保证金退款、候补递补及并发库存竞争。
14. 检查每个异常是否有明确状态、处理人、审批依据及最终处理结果。

验收通过条件是：正常交易能够完整闭环；不满足前置条件的交易能够被拦截；所有关键业务数据能够关联、核对和追溯。

# 11. 建议的开发顺序

## 阶段一：基础数据及权限

- 员工、角色、权限。
- 企业客户和联系人。
- 商品、库存批次及文件。
- 操作日志与基础审批。

## 阶段二：竞价业务闭环

- 活动创建和规则版本。
- 企业申报及资料审核。
- 评审结果、中选及候补。
- 保证金登记和财务核验。

## 阶段三：订单履约闭环

- 合同及交易确认。
- 销售订单、应收计划和收款核销。
- 库存锁定、出库审批及物流签收。
- 退款、取消和售后处理。

## 阶段四：测试及上线准备

- 端到端业务测试。
- 权限与数据隔离测试。
- 并发、幂等及数据一致性测试。
- 备份恢复和异常处理演练。
- 用户培训、操作手册和上线审批。

# 12. 上线前必须完成的管理决策

以下事项没有正式结论前，不应直接写死在代码中：

1. 竞价评审公式、报价排序及并列处理方式。
2. 客户采购能力的认定标准。
3. 保证金的金额、收取方式、退还期限和争议处理。
4. 中选后合同签署及付款期限。
5. 逾期、取消和候补递补规则。
6. 分批付款及分批发货条件。
7. 库存的权威数据来源及调整审批制度。
8. 交易异常、合同变更和退款的审批矩阵。
9. 审计数据、合同文件和客户资料的保存期限。
10. 高端硬件销售所需的客户及交易合规审核规则。

建议由业务负责人牵头，财务、法务、仓储及技术共同评审，并为每项决策指定负责人、截止时间和最终批准人。

**本 PRD 的最终目标：** 建立一套以真实需求审核为前置、以竞争性分配为核心、以合同和资金校验为保障、以库存及发货控制为执行机制、以完整审计链为责任依据的高端硬件交易平台。
