## chat rep

**是同一套机制**——就是开源 Endora 的 **Feature 167（locale-in-path）**，你们是 cherry-pick 合进来的，不是另写一套。

共同逻辑：

1. **URL 前缀 = 当前语言**（middleware 解析，`getServerContext` 取 path 语言）
2. **切换语言 = 换到同逻辑路径的另一前缀**（`LocaleSwitcher` + `localizePath`）
3. **站内链接/跳转**走 `LocalizedLink` / `localeRedirect`，避免丢前缀
4. **渠道开关** `prefix_default_language`：开 → 默认语也有前缀；关 → 默认语无前缀（你们生产 `default` 是关的，所以 zh-CN 是 `/...`，en 是 `/en/...`）

和 demo 可能不同的只有**配置与壳层**，不是引擎：

| | 你们小 B | 开源 demo 典型 |
|---|---|---|
| 机制 | 167 | 167 |
| 语言列表 | 渠道里配的 zh-CN / en-US / zh-TW | demo 渠道往往 pl / en 等 |
| Prefix 默认语 | 存量渠道一般关 | 新渠道默认开 |
| UI | Mobii 顶栏 tab、竞价、NavigationBar | demo 自己的 Header/主题 |

所以：**「切语言 → URL 变 → 页面文案跟 URL」= demo/上游 167 同一模型**；差别主要在渠道语言、Prefix 勾选，以及你们业务页是否都接了 `t()`（刚修的 account 就是这类回归，不是另一套路由）。

## 页面内容怎么跟着 tab 变

核心不是「同一页里用 JS 换字典」，而是：**点语言 = 导航到另一个带语系前缀的 URL → 整页按新 URL 重新渲染**。

```
点 zh-TW tab
  → 浏览器打开 /zh-tw/当前逻辑路径（并写 lang cookie，给无前缀入口用）
  → middleware 认前缀，写入当前语言
  → getServerContext().locale = 路径语言（如 zh-TW）
  → 页面用 tForLocale(locale) 取文案；调 API 时带上该 locale
  → 你看到中文/繁中
```

分三层：

1. **切换器**（`LocaleSwitcher`）  
   每个语系是一个普通 `<a href="...">`。href = 当前页逻辑路径 + 目标语前缀（`localizePath`）。点了就是整页跳转，不是只改 state。

2. **谁决定「当前语言」**  
   Feature 167：**以 URL 为准**。cookie / `Accept-Language` 不直接决定已渲染页的语言；它们主要影响「无前缀 URL」时 middleware 往哪 307。

3. **内容从哪来**  
   - 壳层文案：`messages.ts` 里 en / zh-CN / zh-TW…，`tForLocale(locale)(key)`  
   - 商品/CMS 等：请求后端时带渠道 + locale，后端按语言返回翻译  

所以 tab 一变 → URL 变 → locale 变 → `t()` 和接口数据一起变。

对比：**货币切换**是写 cookie + `router.refresh()`，URL 可以不变；**语言**是换 URL。

---

## 和开源项目是否一样？

**机制一样**，都是 Feature 167 这条链路：  
`LocaleSwitcher` → 换前缀 URL → middleware → `getServerContext().locale` → `tForLocale` / API locale。

不一样的主要是**数据与皮肤**，不是开关原理：

- 渠道里配了哪些语言、默认语是否带前缀（`prefix_default_language`）
- 你们多了 zh 文案、竞价页、Mobii Header 等  
- 某页若写成死英文、没用 `t()`，URL 对了字也不换——那是页面接线问题，不是两套切换引擎

**一句话：** 点 tab 换的是「带语言的地址」；页面内容是新请求里用新 `locale` 重画出来的——你们和小 B 开源 demo 在这点上是同一实现。
