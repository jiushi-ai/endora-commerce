## 结论先说

慢不是「两套人马写坏了」，而是**产品形态故意用了两套前端架构**：

| | 大B Admin | 小b Storefront |
|---|---|---|
| 运行时 | **Vite + React SPA**（`react-router-dom`） | **Next.js App Router SSR** |
| 切语系 | 浏览器里 `setLanguage()`，字典已在内存 | 写 cookie → `router.refresh()` → **整棵服务端树重算** |
| 点菜单 | 客户端换路由，多数只拉 API JSON | 每次导航都走服务端渲染 + 后端请求 |
| 根布局 | 静态壳，几乎不重跑 | `force-dynamic`，每请求都跑 `getServerContext()` |

同一仓库、同一平台后端；admin / storefront **分工不同**，不是偶然两套乱拼。

---

## 1. 为什么大B 切语系、点菜单都快？

**大B = 单页应用（SPA）**

- 切语系：`LanguagePicker` 乐观更新 `AppLanguageContext`，文案用已加载的 i18n bundle 立刻重绘；再后台 PATCH 偏好。**不重跑整页 HTML**。
- 点菜单：`react-router` 客户端换屏，壳（侧栏/顶栏）不动，只换内容区 + 按需 API。
- Dev 是 Vite，热更新轻；生产也是浏览器里跑完再请求 API。

体感：点一下几乎「本地换皮」。

---

## 2. 为什么小b 切语系、点菜单都慢，CPU 还高？

**小b = 服务端渲染店面（SSR）**

- 切语系：写 `lang` cookie → `router.refresh()` → **整页 RSC 再跑一遍**（layout 含 Header/Footer/Mega、首页/目录等）。
- 根布局写了 `export const dynamic = 'force-dynamic'`，且每次进 `getServerContext()`（i18n 配置、渠道、主题、模块存在性等），**导航/刷新都会打后端**。
- 为 SEO/首屏正确 `<html lang>`、按 locale 出商品/CMS，这是刻意设计，不是 bug。
- Dev 下 Next 还要编译/水合；client 组件若 `import` 巨大的 `messages.ts`，会再抬高 CPU。

体感：每次像「重新打开一页」，不是「本地换字典」。

---

## 3. 「是不是不同架构 / 不同人拼的？」

- **架构确实不同**，且写在 package 描述里：admin = Vite SPA；storefront = Next SSR。
- **后端与模块边界是统一的**（contracts、modules、平台内核），不是两套无关系统。
- 观感差异主要来自 **SPA vs SSR**，不是「代码质量两套」；开发态会把小b 的慢放大，生产会好一些，但 SSR 仍不可能和大B 一样「瞬间换皮」。
